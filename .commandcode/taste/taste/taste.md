# Taste
- Communicates in Chinese; prefers responses and discussion in Chinese. Confidence: 0.8
- Prefers to replicate the structure and layout logic of an existing screen when creating a new similar page, to keep the UI consistent across related screens. Confidence: 0.9
- Prefers using the project's theme color helper functions (e.g., getOutline, getOnSurfaceSecondary, getOnSurfaceTertiary) rather than hardcoded colors. Confidence: 0.9
- When specifying a UI screen, gives precise pixel-level specs (exact dp spacing, corner radii, max-width ratios, color tokens) and expects the implementation to match them exactly. Confidence: 0.85
- Prefers compact controls that hug their content: input bars should be roughly text height plus small padding (e.g., 5dp vertical), not the taller default Material paddings, and sibling controls (e.g., a send button next to an input field) should be equal height. Confidence: 0.6
- Expects standard keyboard UX on input/chat screens: the IME keyboard pushes the content up (imePadding) and tapping blank space dismisses the keyboard. Confidence: 0.7
- For pages backed by cloud data, expects a ViewModel + ViewModelFactory wired through navigation, with optimistic UI updates that sync to the backend. Confidence: 0.6
- Prefers unread-count badges to be circular, with the theme primary color as background and surface color for the digits, anchored at the top-right corner of the icon (and the same badge style on the bottom "消息" nav tab when a private message arrives), matching WeChat/Xiaohongshu conventions. Confidence: 0.8
- Prefers social interactions (likes, favorites, follows, comments, private messages) to be real-time and backed by the backend rather than locally simulated/mock data. Confidence: 0.85
- Validates real-time/social features end-to-end with a second account: performs the action from another account, switches accounts, and expects the notification list, unread badges, and chat to reflect it immediately. Confidence: 0.7
- When a feature "doesn't work", expects the assistant to verify the actual live backend state (e.g., whether Supabase tables exist and hold data) and find the root cause, not just confirm local builds pass. Confidence: 0.5
- Prefers buttons whose label can change (e.g., 关注 → 已关注 → 发私信) to keep a fixed width with centered content and constant internal padding, so changing the text length never changes the button width or shifts the layout. Confidence: 0.85
- On user-list rows, prefers the followed state to show "发私信" (opens chat with that user) instead of offering an unfollow action in the row — unfollow is not an entry point there — matching Xiaohongshu interaction conventions. Confidence: 0.7
- Expects account-to-account messaging bridges wherever another user is surfaced (follower list rows, post-detail author bar): tapping "发私信" directly creates/opens the conversation with that user and lands on the corresponding ChatScreen. Confidence: 0.6
- In chat screens, prefers avatars to show on both sides: own sent messages display the current user's avatar on the right and peer messages display the peer's avatar on the left — sent messages should not appear avatar-less. Confidence: 0.7
- Expects account switching to be clean and leak-free: session-scoped chat state (peerUid, conversationId) must reset on logout, and account-scoped ViewModels/lists (conversations, notifications) must reload for the new account — seeing the previous account's data or a broken send button after switching accounts is a bug. Confidence: 0.6
- In the conversation list row, prefers the unread-count badge to sit in the top-right column directly below the send-time text (not at the far right edge of the row), and prefers it small/compact (e.g., ~15dp min size, ~9sp digits) rather than large. Confidence: 0.75
