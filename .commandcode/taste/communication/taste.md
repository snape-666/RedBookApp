# Taste

- When handed a menu of alternatives, expects the assistant to state clearly WHICH one it recommends (and why) rather than laying out neutral options and leaving the choice open — a bare "推荐走哪个" after an A/B/C breakdown means the options were presented without a verdict. The preferred verdict favors the general/root-cause fix over a one-off narrow workaround (e.g., fixing the whole machine's broken IPv6 instead of a single hosts-file entry for one domain). Confidence: 0.5
- Explicitly invites the assistant to ask clarifying questions (repeatedly, for however many rounds are needed) before implementing a feature until it can fully understand and 100% satisfy the requirements ("你可以问我问题直到你可以百分百完成我的要求") — the assistant is expected to probe ambiguities (e.g., which model/API, exact prefix semantics, trigger behavior) with concrete pick-one options rather than guessing and implementing on assumptions; the user is happy to answer these questions to align requirements. Confidence: 0.8
- Wants a complete, explicitly ordered handoff checklist of every thing THEY (not the assistant) still has to do — asked for verbatim with "把我要做的全部列出来" and, when only some items remained, re-requested as "剩下没做的需要我做的一次性给我列出来" — rather than prose about what was implemented. The "一次性" wording means all outstanding manual items must be consolidated into a single message (not drip-fed or split across an assistant-done vs. user-todo mix), covering only what is genuinely still pending. Expected shape: numbered steps in dependency order (with ordering constraints called out, e.g. deploy functions before the keys file is deleted), the exact commands to run per step, plus separate clearly-labeled sections for permanent warnings (files/scripts never to re-run because they'd undo the hardening), items now voided/obsolete that can be ignored (superseded earlier instructions), and remaining known gaps left open for a decision (items that need the user's 拍板 but no action from them). Confidence: 0.65
- When given a handoff list of manual steps, needs each step mapped to WHERE it is physically executed, not just what command to run — the terse follow-up "所以我在哪执行这些操作" expects a breakdown by environment: the PowerShell window opened on their own machine (via the Start menu, `cd` into the project dir first; steps like the IPv6 adapter fix need an elevated "以管理员身份运行" window), the browser → Supabase Dashboard (SQL Editor for pasting the migration SQL; the Edge Functions page for creating/hosting functions without the CLI; Secrets under Project Settings), and the phone/emulator for acceptance testing — and it should say plainly which steps only the user can do themselves (e.g. the interactive `supabase login` browser authorization) versus which the assistant can run for them once that's done. Confidence: 0.6
- When handing over a command or code snippet that contains values the user must supply (credentials, tokens, ids), bare Chinese placeholder words are read as literal fixed values: the user saw `你的账号`/`你的密码` in a curl example and asked "为什么是固定的" instead of substituting their own, because to them a real app's accounts are dynamic and shouldn't be hardcoded. So delimit placeholders unambiguously and say explicitly "replace with your own value / this is not a fixed value" — and clarify that the snippet isn't part of the app and that the app itself never hardcodes credentials. Confidence: 0.5
- When checking in on whether a server-side/backend change is in effect (e.g. a terse "所以连RLS成功了吗,我要做什么"), the user conflates "code written in my local repo" with "live on the deployed backend", so the expected answer leads with the true current state — explicitly stating that nothing has been pushed/deployed yet until the manual steps run (e.g. RLS already on from before but the new policies not applied, no Edge Functions deployed, phone still running the old APK) — and warns that the app stays broken in intermediate partial states (running only the SQL without shipping the new APK won't work either). It then repeats the ordered steps in dependency order with the exact commands, and closes with the likely places the user could get stuck plus the fallback path for each (e.g. Dashboard instead of CLI, psql direct-connect instead of the SQL Editor), inviting them to send the error from whichever step blocks them. Confidence: 0.6
- When receiving instructions for a manual procedure, asks for the level of detail to be spelled out click-by-click ("第一步具体怎么做,说详细点") — a one-line step name is not enough; the expected shape is a numbered walkthrough of every concrete action including where in the UI to look (which menu/sidebar item, which button label, in what order), what to expect after each action, how to verify it worked, and what to do if a described button/element isn't found (send a screenshot/description). The user is not assumed to fill in any implicit sub-steps themselves. Confirmed in practice — told to find a "Verify JWT" toggle, the user came back with just "没找到JWT" — so UI-element contingencies should be spelled out proactively (multiple plausible locations/names per element, plus a "deploy anyway and come back to it if it errors" fallback). Recurred when asked to do a third-party dashboard task ("验证域名的Resend这一步具体怎么操作"), confirming the same click-by-click expectation for any manual/external-console procedure. Confidence: 0.7
- When handing over terminal commands, prefers them split into single, one-at-a-time commands to paste and run sequentially ("把命令给我分成一次一次的") rather than one large multi-line block, because pasting a whole script block into their terminal doesn't run — the assistant should number each command, tell them to paste one, press enter, and wait for the result before the next, and describe what output to expect (and what to copy out of it, e.g. the access_token) before moving on. Confidence: 0.6
- When instructing the user to fill in a config/settings form (external console), wants the exact literal value pinned for EVERY field, and especially the non-obvious ones called out explicitly — a critical field merely mentioned in passing inside a long checklist gets filled with a guess and the whole flow fails (blamed with "你不早说 username 填的是邮箱,我填的是别的"). So for each field give a copy-paste value (e.g. Username = the full Gmail address, identical to Sender email), flag the counter-intuitive ones as the actual cause of the error, and state the invariant constraints (which two fields must match exactly, what the value must NOT be) instead of leaving the user to infer it from a descriptive note. Confidence: 0.6
- When a fix needs BOTH manual/external-console setup and code changes, wants the two separated in time: the user asks for the operational walkthrough first and explicitly defers the implementation ("现在给我用谷歌那条路的操作步骤,代码你后续再写") — so deliver the full browser/dashboard steps they can start doing now, explicitly call out which step cannot yet be verified until the code lands, briefly state what the upcoming code change will do as an expectation, and only write the code afterward. Confidence: 0.5
- When a change involves content the user must paste into some external UI (an email template, a config field, a snippet), wants the COMPLETE, ready-to-paste artifact handed over directly rather than a prose suggestion, a description of what to write, or an offer to produce it — a suggestion like "建议顺便把邮件模板改成中文" with only a sketch gets the immediate follow-up "直接把换成中文模板的代码发给我". Deliver the exact final strings (e.g. both the subject heading and the full body markup) in paste-ready form, and note the pitfalls inline (which placeholder/variable must be kept verbatim, what was intentionally omitted and why). Confirmed again, and the shape of the ask is now clearer: the user pastes the CURRENT version of the artifact (e.g. the whole existing email-template body) and says "直接给我修改后的完整代码" — so when the user supplies existing content, the expected reply is the ENTIRE final artifact to replace it wholesale (labeled as such, e.g. "整段替换"), not a diff/patch of only the changed lines, not prose about which lines to change, and not a partial excerpt. Confidence: 0.7
